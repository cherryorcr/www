# arxiv 类别增量划分设计（协议修正 ④）

日期：2026-09-10
动机：arxiv 现用 temporal 三阶段（每阶段 40 类全在），与 Cora/Citeseer 的类别增量**不是同一种流**，结论不可并列，且同分布下测不出遗忘。本文件设计改为类别增量并统一测试协议。
状态：设计稿，待执行。**执行后旧 temporal 结论不得与新结果混用**，temporal 版保留为边界实验。

## 1. 关键前置事实：arxiv 40 类极度长尾

统计（pool = 排除 dev/test 的 135,473 节点）：

| 排名 | 类别 | pool | dev |
|---:|---|---:|---:|
| 1 | cs.cv | 21,844 | 2,746 |
| 2 | cs.lg | 17,775 | 2,191 |
| 3 | cs.it | 17,059 | 2,131 |
| 4 | cs.cl | 9,532 | 1,193 |
| 5 | cs.ai | 6,285 | 790 |
| … | … | … | … |
| 36 | cs.ar | 325 | 42 |
| 37 | cs.oh | 311 | 46 |
| 38 | cs.os | 102 | 16 |
| 39 | **cs.gl** | **24** | **1** |

**最大/最小 = 910×，中位数仅 1,661。** 前 3 类占 pool 的 **41.8%**，后 20 类合计仅 6.9%。

### 这带来三个必须处理的问题

**问题 A：均分类别会导致阶段规模相差 10 倍以上。** 若按"每阶段 13 类"均分，最后一段可能只含几千节点，而第一段含 5 万——预算（rate×累计 pool）会随之剧烈波动，不可比。

**问题 B：小类的 Macro-F1 极不稳定。** `cs.gl` 在 dev 上只有 1 个节点，其 F1 只能是 0 或 100，直接进入宏平均就是掷硬币。**这是当前 temporal 设定下同样存在的问题**，此前并未处理。

**问题 C：类别间的语义层次会被打散。** temporal 划分下同类领域往往聚集；若按规模贪心分配，`cs.cv`/`cs.lg` 这类近邻可能被拆到不同阶段，人为增加难度。

## 2. 三种候选方案

### 方案 A（推荐）：按规模贪心均衡 + 类别数均衡的联合目标

目标函数同时约束三件事：

```
minimize  Σ_stages |size(stage) - size_target|²          # 规模均衡
        + λ₁ Σ_stages |nclass(stage) - nclass_target|²   # 类别数均衡
        - λ₂ · cohesion(stage)                           # 语义凝聚力（鼓励同领域同阶段）
```

实现：先按 `cs.<field>` 大类分组（arxiv 的 40 个二级类可归为若干一级领域），在领域内按规模排序，用贪心（每次把当前最大的未分配类放进当前最小的阶段）分配。

**预期切分**（三阶段，目标各 ~45k pool、13–14 类）：

| 阶段 | 类别数 | 目标 pool | 累计预算（5%） |
|---|---:|---:|---:|
| s0 | 13 | ~45,000 | 2,250 |
| s1 | 13 | ~45,000 | 4,500 |
| s2 | 14 | ~45,473 | 6,773 |

优点：与 Cora/Citeseer 同构；规模均衡；领域凝聚力尽量保留。
缺点：任何均衡切分都无法消除长尾，小类仍会进入宏平均。

### 方案 B：保留 40 类，但显式处理长尾

在 A 的基础上追加两个协议决定（二选一）：

- **B1（不合并）**：如实报告全部 40 类的 Macro-F1，**并同时报告"去掉 pool<500 的 6 个类"后的 Macro-F1**（双指标）。承认长尾是 arxiv 的固有属性，不做人为简化。
- **B2（合并）**：把 pool<500 的类合并为一个 `cs.other`，标签空间从 40 降为 ~35。

**推荐 B1。** 理由：合并会改变标签空间，使"与官方 GraphCLIP 对比"和"与同领域工作对比"都失去基准；而双指标既如实又能说明问题。这与本项目"如实报告、不掩盖边界"的一贯立场一致。

### 方案 C（不推荐）：按类别数均分

实现最简（13/13/14），但阶段规模相差数倍，预算不可比。

## 3. 统一测试协议（三数据集一致）

```
dev  = node_id % 10 == 1     （16,935 节点，用于 checkpoint 与选点）
test = node_id % 10 == 2     （16,935 节点，一次性读取，confirmation_accessed: true）
pool = 其余                    （135,473 节点，供凝聚）
```

与 Cora/Citeseer **完全相同的规则**。这意味着 arxiv 的 test 分区将首次被读取——**当前 arxiv 的 test 从未读过（`test_accessed: false`），所以这是一次干净的首次确认**，不是重复消费。

## 4. 执行后必须重新报告的对照

改协议后，以下必须以**新协议重新跑**，不能沿用旧数字：

| 对照 | 旧（temporal） | 预期变化 |
|---|---|---|
| append vs full_history | append 17.89 vs fh 18.52（−0.63） | **差距预计拉大**——类别增量下 full_history 应受类别主导效应拖累，与 Cora/Citeseer 同向 |
| append vs raw 累计直训 | raw 领先 3pp | 预计类似或更大 |
| recluster 的塑性优势 | 未测（temporal 下无类别新增） | 类别增量下应显现 |
| 扰动模块（v1.2） | 静态有效（+1.64） | 持续场景下是否仍有效——**未测** |

**这一点很重要**：新协议很可能会让方法与基线的差距变大，也就是**结论对我们更有利**。但这必须作为"协议变更后的新结果"呈现，并在论文中明确说明为何变更（与其它数据集同构、能测遗忘）。

## 5. 必须预防的三个陷阱

**陷阱 1：阶段难度的偶然性。** 若某一阶段恰好装了几个近邻大类（如 cv+lg+it 同段），该阶段会更难，而另一阶段全是小类。**必须报告阶段的类别组成**，并在论文中说明该切分不是"挑出来对我们有利的"。建议：**预先注册切分方案**（本文件即预注册），执行后不再调整。

**陷阱 2：与 temporal 结论的混用。** `ARXIV_CONTINUAL_AND_RAW_ZH_2026-09-10.md` 的全部数字属于 temporal 协议，改协议后该文档须标记为"边界实验"，其结论（分阶段构造的优势是类别增量特有的）**仍然有效且更显重要**——因为它正是由 temporal 与类别增量的对比得出的。

**陷阱 3：小类的宏平均噪声。** 必须在结果 JSON 中记录每类节点数与每类 F1，以便审稿人核查宏平均是否被 1–2 个样本的类主导。
