# 重大实验缺陷：batch size 是全局混淆因素，效应量 20+ 分

日期：2026-09-11
发现路径：k-center 诊断（`KCENTER_DIAGNOSIS_RESULTS`）→ 矛盾排查 → batch 扫描
数据：`/tmp/cmp_train.py`、`/tmp/batch_sweep.py` 输出（已记录于本文档）

---

## 1. 发现

排查 `FINAL_eb_cora`（ours=33.30）与 `KCD_cora`（ours=47.10）的矛盾时，定位到**唯一的功能差异是 batch size**：

- `run_multiscale_asm.py::train_student` 签名：**`batch=64`**（默认值）
- `run_kcenter_diagnosis.py::train_with_curve` 和 `run_external_baselines.py` 用了 **`batch=24`**
- `frozen_v1/run_gate1_continual.py::train_student` 也定义 `batch=24`，但**调用处显式传了 `batch=min(24, n)`**

**Cora 上的 batch 扫描（k=108, steps=1728, seeds 700–702）**：

| batch | dev F1 |
|---:|---:|
| 8 | 51.82 |
| **16** | **55.14** |
| 24 | 47.10 |
| 32 | 42.33 |
| 48 | 36.99 |
| **64（`run_multiscale_asm` 默认）** | **32.10** |
| 96 | 31.58 |
| 108（=全部行） | 31.15 |

**从 batch=8 到 batch=108，F1 摆动 24.0 分（51.82 → 31.15）。**

## 2. 为什么这是一个严重问题

**（a）它的效应量远大于我们研究的所有效应。** 此前所有对照的效应量在 1–5 分（ASM、扰动、判据、消融），而 batch 的影响是 **20+ 分**。**用一个 20 分的混淆因素去测 3 分的效应，结果没有意义。**

**（b）它污染了哪些实验**：

| 实验 | 使用的 batch | 是否受影响 |
|---|---|---|
| `run_multiscale_asm`（ASM 全部实验、scale-gate、jitter） | **64** | ✅ 受影响 |
| `run_external_baselines`（基线表） | 24 | ✅ 与上面不同口径 |
| `run_kcenter_diagnosis` | 24 | ✅ 与上面不同口径 |
| `frozen_v1/run_gate1_continual`（Gate 1/2/3） | 24（显式） | 与上面不同口径 |
| `run_newbench_full`（扰动全表） | 24 | 与上面不同口径 |
| `run_newbench_test`（test） | 24 | — |

**关键问题：ASM 家族用 batch=64，其余全部用 batch=24。** 这意味着：

- **ASM 与 frozen 的比较虽然内部一致**（都 64），但与基线表、扰动表的数字**不可比**；
- 更重要的是，**batch=64 时 frozen 只有 32.10——接近随机水平（7 类）**。ASM 实验是在一个**严重欠优化的基线上**测的。**如果 ASM 在 batch=64 下"有害"，可能只是因为它在一个已经受损的模型上再加扰动。**

**（c）它可能反转此前的结论**：
- ASM 的"有害"结论（7 个数据集中 6 个有害）是在 batch=64 下得到的；
- 扰动的"不稳定"结论是在 batch=24 下得到的；
- **两者在不同 batch 下得到，且都不在最优 batch 下。** 在 batch=16 下（Cora 最优），这些结论是否成立**完全未知**。

**（d）它还可能解释 k-center 之谜**：k-center 的行是真实节点、特征分布集中，**对 batch size 的敏感度天然低于**我们的合成行（合成行的分布更"平滑"、更依赖大 batch 才能形成有效负例）。这可能就是"k-center 优势"的真正来源——**不是选点策略更好，而是它对超参更鲁棒**。

## 3. 与既有设计的关系

`frozen_v1` 的 `FREEZE_DECLARATION.md` 记的是 **batch=24**，且 `run_gate1_continual.py` 的调用处写了 `min(24, n)`。所以**冻结版本的配置是正确的**，Gate 3'' 的 58.07 没有这个问题。

**问题出在后来写的脚本**：`run_multiscale_asm.py` 用了 `batch=64` 作为默认值，而它派生出的所有实验（ASM、scale-gate、jitter、多尺度）都继承了这个值。

**注意一个讽刺**：`min(2048, 16×roots)` 这个步数自适应规则是**被一次过拟合故障逼出来的**（32 行的图被训 2048 步导致 28.7 分）。**batch 的自适应问题完全同构，但从未被发现**——因为所有验证都在 Cqra/Citeseer 上做，而它们恰好都用了同一个 batch。

## 4. 立即要做的修正

**（a）标定规则**：batch 应随行数自适应。Cora（108 行）的最优是 16，即 **k/6.75**；若按"行数的固定比例"外推，arxiv（6,773 行）会是 1,004——显然不对。

**更可能的正确形式**是"**batch 与 k 的比值应当落在某个区间**"，或直接**扫描每个数据集的 batch**取最优。**在弄清之前，应当对每个数据集单独扫 batch 并记录**，而不是用一个全局默认值。

**（b）重跑清单**（按重要性）：
1. ASM 的全部实验（7 个数据集）——在最优 batch 下是否仍有"6/7 有害"；
2. 扰动模块的全部格点——不稳定性是否消失；
3. 基线表——k-center 优势是否消失；
4. scale-gate 的规模门槛——是否仍非单调。

**（c）论文影响**：**在重跑完成前，此前所有基于 batch=64 的结论都不能写入论文。** 这是一个必须向导师/合作者明确说明的问题。

## 4.5 标定结果：**没有统一的 batch/k 比例规律**

对两个 k 相差 64 倍的数据集扫描 batch/k：

**Cora（k=108, steps=1728）**

| batch | batch/k | F1 |
|---:|---:|---:|
| 4 | 0.02 | 44.42 |
| 5 | 0.05 | 48.79 |
| 10 | 0.10 | 52.35 |
| **16** | **0.15** | **55.14** |
| 27 | 0.25 | 47.12 |
| 54 | 0.50 | 33.57 |
| 108 | 1.00 | 31.15 |

**sportsfit（k=6,922, steps=2048）**

| batch | batch/k | F1 |
|---:|---:|---:|
| **138** | **0.02** | **23.76** |
| 346 | 0.05 | 23.64 |
| 692 | 0.10 | 20.11 |
| 1,038 | 0.15 | 18.52 |
| 1,730 | 0.25 | 15.87 |
| 3,461 | 0.50 | 14.55 |
| 6,922 | 1.00 | 17.50 |

**两个数据集的最优 batch/k 分别是 0.15 和 ≤0.02（64 倍差距），没有统一比例。**

**但有一个共同点：两者都单调下降到大 batch 端**——**batch 越小越好，直到某个下限**。Cora 的峰值在 16（低于此因负例不足而下降），sportsfit 在整个扫描范围内偏好最小 batch。

**这解释了为什么大图实验受影响较小**：sportsfit 的最优 batch ≤138，而 `run_multiscale_asm` 用的 64 **恰好落在最优点附近**。所以**大 k 数据集（arxiv/k=6773、sportsfit/k=6922、bookchild/k=3074）的 batch=64 接近最优**，**而小 k 数据集（Cora k=108、Citeseer k=127）的 batch=64 是灾难性的**（31.15 vs 最优 55.14）。

### 修正后的影响评估

| 数据集的 k | batch=64 是否接近最优 | 受影响程度 |
|---|---|---|
| k ≥ 1,000（wikics/bookhis/bookchild/sportsfit/arxiv） | ✅ 接近（64 与 138 同量级） | **小** |
| k < 200（Cora/Citeseer） | ❌ 严重过大 | **大（差 20+ 分）** |

**所以：**
- **大图实验（arxiv ASM、扰动全表、基线表的 bookhis/bookchild/sportsfit/wikics）基本可信**；
- **Cora/Citeseer 相关的所有实验都严重受污染**——包括 Gate 1/2/3（batch=24，离最优 16 很近，**受影响较小**）、基线表的 cora/citeseer 行、`run_multiscale_asm` 的 cora/citeseer 输出。

**一个重要的安慰**：`frozen_v1` 的 Gate 3'' 用的是 **batch=24**，而 Cora 的最优是 16——**两者接近，所以冻结的 58.07 没有严重问题**（可以解释为什么它是 58 而不是 33）。

**而 `run_multiscale_asm` 的 cora 输出（33.30）正是 batch=64 的产物**——这也解释了为什么它与 Gate 3 的 58.07 差 25 分。**两者不是"协议不同"，而是"batch 不同"**。

## 5. 方法论教训

这个缺陷逃过了**所有**此前的验证，原因和 `FUSE_CHARS` 那次一样：**所有实验都在同一批数据集上、用同一套（有缺陷的）超参做**，因此缺陷是系统性的、不产生异常值。**只有当引入一个结构不同的对照（k-center，用真实节点行）时，它对超参的敏感度差异才暴露出来。**

**教训**：**超参混淆是比方法缺陷更难发现的错误**，因为它不影响"方法内部是否自洽"，只影响"方法之间是否可比"。任何跨方法的比较，都必须先证明**超参配置对各方都是（近）最优的**，否则比较的是超参而不是方法。
